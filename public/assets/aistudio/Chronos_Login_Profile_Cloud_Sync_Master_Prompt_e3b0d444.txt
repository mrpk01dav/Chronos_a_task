PHASE 3 — CLOUD DATA AND SYNCHRONIZATION
Use Cloud Firestore if compatible with the audited architecture, with a documented data model and user-specific security rules.

Requirements:
- Use a stable authenticated user ID to associate data with its owner.
- Store user profiles, tasks, recurrence settings, completion history/remarks, and relevant preferences.
- Preserve task IDs, due dates, time-zone semantics, recurrence rules, reminder configuration, timestamps, and completion history.
- Support synchronization between web and native Android.
- Keep offline task access where feasible using the existing local storage and Room database.
- Handle offline creation, edits, deletion, reconnecting, retries, concurrent edits, duplicate writes, and conflict resolution.
- Use stable IDs and idempotent operations so repeated sync attempts do not create duplicate tasks.
- Use deletion markers or another documented strategy where necessary to prevent deleted tasks from reappearing.
- Document which fields are server-authoritative and how conflicts are resolved.
- Never rely on client-side UI filtering as the only access-control mechanism.
- Enforce user isolation through backend/database security rules and test those rules.
- Do not introduce a second database or sync framework without explaining why it is necessary.

Cloud synchronization does not automatically guarantee that local notifications fire. Keep platform-specific reminder scheduling and permissions working independently.

PHASE 4 — SAFE EXISTING-DATA MIGRATION

1. Identify and back up the existing local task records.
2. Inspect IndexedDB/local storage for web and Room for Android, as applicable.
3. Count and validate tasks, completion records, recurrence rules, reminders, and preferences.
4. Detect malformed records, duplicate IDs, conflicting records, and schema differences.

7. Preserve stable IDs where possible and make migration idempotent.
